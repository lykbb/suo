# AI 功能 PRD 补充章节

需求里有生成、理解、检索或 Agent 执行时，在普通 PRD 之外补上这些章节。普通 PRD 讲清“产品怎么表现”；AI 功能还要讲清“模型该怎么表现、怎么判断它做得好不好、做不好时怎么办”。

只写与当前功能相关的章节。设计层面的取舍（要不要用 AI、选什么架构）见 `pm-ai-product-design`；评测集怎么做见 `pm-ai-evaluation`。

## A1. 为什么用 AI

- 用户任务、输入和期望结果。
- 不用 AI 的做法（规则、模板、搜索、人工）现在做到什么程度，AI 要比它好在哪里。
- 结果出错的代价：用户能否看出错误、改起来难不难、会不会造成实际损失。

## A2. 模型行为规格

这一节是 AI 功能 PRD 的核心，相当于普通功能的“规则”。

| 项目 | 写什么 |
| --- | --- |
| 任务 | 一句话说清模型要完成什么，写成可判断的结果 |
| 输入 | 来源、长度上限、超出时怎么处理、是否包含敏感信息 |
| 输出 | 格式、结构或字段、长度、语言、是否必须附来源 |
| 必须做到 | 几条可判断的要求，例如“每条结论附资料出处” |
| 不得出现 | 例如编造原话、给出未经资料支持的数字、执行未授权的操作 |
| 需要先澄清的情况 | 输入含糊、缺少关键信息时，问什么、怎么问 |
| 应该拒绝或说明做不到的情况 | 超出能力、越权、资料里没有答案 |
| 不确定时怎么表达 | 例如说明“资料未提及”，而不是猜一个答案 |

可以附几组好与不好的输出示例，并标明“示例”。示例会被模型模仿，所以要和规格一致。

## A3. 工具与权限（Agent 才需要）

| 工具 | 能操作什么 | 需要用户确认吗 | 失败或重复调用时怎么办 | 能否撤销 |
| --- | --- | --- | --- | --- |

写入、删除、发送、支付类操作单独说明前置条件和成功判定。“完成”以工具的实际结果为准，不以模型说“已完成”为准。

## A4. 评测与上线门槛

- 评测集：案例类型和数量、来源（真实任务、线上失败、构造案例）。
- 评分方式：哪些用规则判断，哪些用评分细则，哪些需要人工。
- 门槛：按类型分别设定，标明“必须达到”和“希望达到”；没有基线时写建议值并注明“待共同确认”。
- 一票否决项：例如编造来源、越权修改、泄露隐私，出现一次即不通过。
- 回归：改提示词、换模型、更新资料后必须重新跑哪些案例。

## A5. 失败与兜底

| 失败情况 | 用户看到什么 | 系统怎么处理 | 是否转人工或给替代方案 |
| --- | --- | --- | --- |
| 回答错误或缺少依据 | | | |
| 资料里没有答案 | | | |
| 过度拒绝 | | | |
| 超时或很慢 | | | |
| 模型服务不可用 | | | |
| 工具调用失败 | | | |

用户需要能核对、修改和撤销 AI 的结果；长任务要能停止，停止后保留已经完成的部分。

## A6. 成本与延迟

- 一次完整任务调用几次模型、大约用多少输入和输出，按什么口径估算。
- 单次任务的成本上限，超出时怎么处理（截断资料、换小模型、提示用户）。
- 延迟目标看完整任务和慢的那部分请求，不只看第一个字出现的时间。
- 价格和模型能力以当前官方资料为准，写明查询日期。

## A7. 数据与隐私

- 用到哪些数据，用户是否授权，是否会发送给第三方模型服务。
- 日志里记录什么、不记录什么（原文、密钥等敏感内容）。
- 数据保留多久，用户删除后是否同步删除。
- 资料和网页里夹带的指令只当作内容处理，不改变系统规则；权限由系统落实，不只靠提示词约束。

## A8. 版本与监控

- 记录提示词、模型、知识库和工具的版本，每次变更说明原因并跑回归。
- 上线后观察：任务完成情况、失败类型、用户修改或重试的比例、投诉，以及成本。
- 回滚条件：哪些信号出现时退回上一个版本。

## A9. AI 功能的验收写法

验收要能被检验，并且说清在什么样本和条件下检验。

- 给定【评测集名称和版本】，当使用【提示词与模型版本】运行，则【某类案例】的通过率达到【建议值，待共同确认】，且一票否决项为零。
- 给定资料中没有用户问的信息，当用户提问，则回答说明资料未提及，不给出推测的具体数字。
- 给定模型服务不可用，当用户发送请求，则提示无法连接和可以采取的操作，已输入的内容保留。

## 示例：从访谈纪要提炼用户问题

以下是示例，说明一条 AI 需求写到什么程度；数值都待确认，不是真实数据。

**任务**：从用户选中的访谈纪要中，提炼受访者遇到的问题，每个问题附原话和出处。

**输入**：一到十份访谈纪要（文本或 PDF 提取的文字）。超过上下文上限时，先告诉用户哪些内容没有读到，再处理已读部分。

**输出**：问题列表。每个问题包括：问题描述、涉及的受访者、原话摘录、出处（文件名和位置）。同一问题合并，并注明提到它的人数。

**必须做到**：原话逐字摘录；每个问题至少有一处出处；没有读到的文件明确列出。

**不得出现**：改写后当作原话；把研究者的推测写成受访者的说法；给出“大多数用户”之类资料无法支持的比例。

**需要澄清**：用户没有选中任何纪要时，提示先选中资料，不凭空生成。

**验收**
- 给定一份包含三个明确问题的纪要，当用户请求提炼，则三个问题都被列出，且每个都附原话和出处。
- 给定两份说法相互矛盾的纪要，当用户请求提炼，则矛盾被单独指出，而不是只保留其中一种说法。
- 给定评测集中的【待确认】个案例，当前版本的出处正确率达到【待确认】，编造原话的次数为零。
