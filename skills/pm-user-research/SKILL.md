# 用户研究与访谈分析

## 从决定开始

先明确研究要支持哪个决定：问题是否重要、哪些人需要、现有流程哪里卡住、方案能否使用，还是用户愿不愿承担成本。研究问题应能改变选择；“了解用户”不足以指导招募和提纲。

已提供真实访谈时先分析，不让用户重做研究。数据不足时交付可执行研究计划，并标清哪些判断仍是猜想。

## 选择方法

| 要回答的问题 | 合适的方法 | 不能单凭它证明的事 |
| --- | --- | --- |
| 为什么发生、用户怎么解决 | 围绕最近实际经历的访谈、情境观察 | 总体人群占比 |
| 用户能否找到入口并完成任务 | 带真实任务的可用性测试 | 长期留存、付费需求 |
| 行为发生多少、在哪步流失 | 有定义和质量检查的行为数据 | 行为背后的原因 |
| 是否愿意投入时间或金钱 | 预约、试用、迁移或支付等真实承诺 | 承诺一定转化成长期使用 |
| 方案是否改善结果 | 对照实验或适合场景的前后验证 | 未控制因素下的确定因果 |

## 招募与样本

按最近行为、任务频率、环境和使用限制筛选，不只按年龄或职位。覆盖当前用户、未采用者、流失者和使用替代方案者中对本次决定重要的人群。

明确样本来自哪里、谁没有被覆盖。不要给“访谈 5 人就证明市场成立”这类保证；根据风险、群体差异和新信息是否仍出现决定是否补样。

## 访谈提纲

围绕最近一次实际经历：触发事件 → 目标 → 操作过程 → 障碍 → 替代办法 → 结果 → 代价。请用户展示真实材料或复述具体步骤；不要求其提供敏感资料。

好问题：“最近一次整理访谈是什么时候？从拿到录音到输出结论，你具体怎么做？”

避免：“如果有一个智能工具替你整理，你会不会用？”这只能得到低成本表态。不要先介绍方案再要求用户认可。需求不是用户随口点名的功能，应回到任务和约束。

追问有价值的信息：上次发生时间、频率、失败后果、谁参与、花了多少时间、为什么选那个替代办法。用户说“经常”时请求具体例子；无法量化就保留原表述，不代填次数。

## 可用性研究

给目标和情境，不把操作步骤写进任务。例如“找到上次访谈中关于支付的问题”，而非“点击搜索按钮输入支付”。观察成功、耗时、求助、错误与恢复；提示后完成不能与独立完成合并计算。

区分功能缺失、入口不被发现、概念不被理解、结果不被信任。记录设备、环境和原型限制，避免把原型故障判断成产品需求。

## 分析与交付

先提取证据，再归纳主题。每个洞察包含：目标人群、情境、实际行为、障碍或动机、来源、反例、对产品的意义。多个解释都合理时说明分歧，并设计能区分它们的后续验证。

交付研究目标、对象与限制、关键发现、证据和建议；需要执行时附招募条件、提纲、记录方式及分析方法。只引用确实提供的原话，不合成“代表性用户说过的话”。

## 完成标准

研究问题对应决策；提纲无明显诱导；样本限制可见；洞察能追溯到观察；建议没有把定性发现冒充总体统计，也没有把喜欢、需求和实际行为混为一谈。
