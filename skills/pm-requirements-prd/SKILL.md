# 需求拆解

把“想做一个功能”变成团队可以讨论和估算的需求底稿。本技能负责问题、流程、规则与范围；写完整 PRD 时接续使用 `pm-prd`。用户直接要求 PRD 时可以直接调用它，不强制先走一遍拆解。

## 从问题到任务

读取用户给出的反馈、资料和已有决定。区分用户原话、真实困难、期望结果和用户提出的解法；事实保留来源，推断写出依据，未验证判断标明假设。沿用已有来源编号，没有编号时建立 `SRC-ID`。

确认谁在什么场景要完成什么任务、现有做法及其成本、预期结果和已经确定的边界。保留用户明确作出的决定，仅对会改变方案的缺口或矛盾提问；其他部分继续完成。

按端到端任务拆流程：进入条件 → 输入 → 用户动作 → 系统反馈 → 结果 → 后续动作。功能模块列表不能替代用户流程。

## 需求清单

沿用已有 `REQ-ID`，为新需求分配稳定编号，后续修改不重新编号。每项需求写清：

- 对应问题及 `SRC-ID`；用户或角色、触发条件和期望结果。
- 输入来源、校验、权限、业务规则、状态变化和输出。
- 与已有功能、卡片或流程的依赖和冲突。
- 可观察的验收条件，用 `AC-ID` 与需求对应。
- 本版包含、明确不做和待确认事项；优先级沿用已有决定，需建议时说明依据。

按实际场景补齐首次使用、空状态、重复操作、部分失败、超时、取消、撤销、并发修改、权限不足、网络中断和重启恢复。只列适用项，不机械填满所有异常。

长任务明确进度、停止后的状态、成果保留与重试方式；保存明确发生时机、失败提示与冲突处理。涉及删除时区分移除引用、进回收站和物理删除；文件流程区分原件、编辑稿和导出结果。

## AI 功能边界

涉及生成、检索或 Agent 操作时，拆清输入与上下文、可执行操作、证据要求、禁止结果、失败降级和人工接管条件。正式 PRD 的模型行为与验收规格由 `pm-prd` 结合其 `references/ai-feature-prd.md` 完成；设计取舍和评测分别使用 `pm-ai-product-design` 与 `pm-ai-evaluation`。

## 交付与衔接

交付与规模相称的需求清单、关键流程、范围及有影响的未决问题。小修改可只给改前、改后、规则和验收，不重写整份文档。

需要正式 PRD 时，把来源、已确认的目标与范围、`REQ-ID` / `AC-ID`、流程、风险及未决问题交给 `pm-prd`，保留这些编号与决定。用户已经要求整份成稿时继续完成，不能只交底稿再让用户重复请求。
