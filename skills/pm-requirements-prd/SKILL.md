# 需求拆解与 PRD

## 目的

让设计、工程、测试与业务对产品行为达成一致。PRD 的质量不是页数，而是目标是否明确、规则是否无歧义、关键场景能否实现与验收。

## 组织需求

先确认目标用户、场景、现有问题、预期结果和已确定范围。保留用户已经作出的决定；仅把有冲突或证据不足的决定拿出来讨论。

从端到端任务拆流程：进入条件 → 操作 → 系统响应 → 结果 → 后续动作。功能模块不能替代用户流程；列了上传、搜索、导出仍可能遗漏用户如何完成一次真实工作。

每项核心需求写清：

- 谁在何种条件下执行什么任务，产生什么结果。
- 输入及来源、必填/选填、校验、权限、状态变化和输出。
- 用户界面行为，以及必须满足的业务约束。
- 异常和恢复方式，相关数据与埋点。
- 验收标准及本版本范围。

## 关键边界

按场景考虑，不机械堆全套条目：首次使用、无数据、重复操作、部分失败、超时、取消、撤销、并发修改、权限不足、网络中断、会话切换、重启恢复。涉及文件或文档时说明原件、编辑稿和导出结果的关系。

长任务明确进度、停止后的状态、结果保留和失败重试；保存明确何时发生、失败如何提示、冲突如何处理。涉及删除时区分移除引用、进回收站、物理删除和共享内容。

涉及多状态流程，用状态表说明允许动作、转移条件和副作用。不能让同一行为在两个章节出现不同规则。

## 验收写法

使用可观察的条件与结果，不写“体验友好”“智能准确”“响应迅速”作为唯一标准。

示例：

> 给定用户未配置模型且输入了文字和附件，当用户发送时，打开模型配置入口；文字与附件保持不变，不发出模型请求；配置完成后由用户再次发送。

性能、准确率、兼容性与可用性目标必须说明测量场景和口径。没有数据时列“建议目标”或“待共同确认的验收值”，不编造现有表现。

## 文档结构

根据需求大小选必要章节：背景与目标、范围、用户流程、具体规则、异常、数据与指标、验收、依赖和开放问题。小改动可只交“改前/改后/规则/验收”。

编号可用于追溯：需求 → 流程节点 → 规则 → 验收案例。写完整可评审的正文；关键未定项说明选择、影响和建议，不用空的“待补充”填章节。

## 评审

检查每个规则是否可实现、可感知、可验证；工程估算由工程侧确认。没有必要将实现库、内部接口或数据库字段写入面向用户的产品文案。

优先指出阻塞交付的歧义与逻辑矛盾，然后处理非阻塞优化。修订时保留有效内容，明确变更和影响范围，不悄悄扩大需求。

## 完成标准

团队无需猜测正常与失败行为；范围、状态、权限和数据一致；每个核心需求都有可执行验收；成功指标对应产品目标，而不是仅统计按钮点击。
